## 一、先看一場事故

> 對應流程圖：〈2. 請求路徑〉的「熔斷中 — 直接跳過」分支，就是這場事故被解掉之後的樣子

假設這個服務有 Redis 當快取，正常流程是：

```
請求進來 → 查 Redis（快，約 1ms）→ 有資料就回傳
                ↓ 沒有
             查 MySQL（約 50ms）→ 寫回 Redis → 回傳
```

現在 Redis 掛了。不是乾脆地拒絕連線，而是**連得上但不回應**（機器還在、程式當住，或網路變成黑洞）。這是最糟的一種掛法。

程式裡設了 `ReadTimeout = 3 秒`。所以：

```
請求進來 → 查 Redis → 等 3 秒 → 逾時 → 查 MySQL（50ms）→ 回傳
```

**每個請求都變成 3 秒起跳。**

### 為什麼這會弄死整個服務

假設流量是 200 QPS。每個請求都卡在 Redis 那裡 3 秒：

```
第 1 秒進來 200 個請求 → 全部在等
第 2 秒又進來 200 個 → 前面 200 個還在等 → 現在 400 個在等
第 3 秒又進來 200 個 → 600 個在等
```

穩定下來會有 **600 個請求同時卡著**。每個都佔用一個 goroutine、一條連線、一份記憶體。

再往下：連線池滿了、記憶體壓力上來、新請求開始被拒絕。

**你的服務死了 —— 但死因是一個「可選的」快取掛掉。** 明明查 MySQL 這條路一直是通的，50ms 就能回應，只是每個請求都要先付那 3 秒的過路費才走得到。

> 補一句：如果 Redis 是乾脆地拒絕連線（connection refused），失敗是毫秒級的，反而沒這麼危險。真正致命的是「連得上但不回應」。

## 二、第一直覺：重試

> 對應流程圖：〈4. 重試主迴圈〉、〈5. backoffDelay〉

看到「呼叫失敗」，最直覺的反應是再試一次。這在**瞬時故障**上是對的 —— 網路抖動、對方剛好在 GC、瞬間過載，這些幾百毫秒後就好了。

但重試有兩個坑。

### 坑一：立刻重試等於補刀

對方正在喘不過氣，你馬上再打一次，是在它最虛弱的時候加重負擔。

所以要**退避（backoff）**：等一下再試，而且每次等更久。

```
第 1 次失敗 → 等 1 秒 → 重試
第 2 次失敗 → 等 2 秒 → 重試
第 3 次失敗 → 等 4 秒 → 重試
```

這叫**指數退避**。程式裡就是 `base << attempt`（左移一位等於乘 2）。

給對方越來越多的復原時間，同時你的總請求量也降下來。

### 坑二：大家會一起重試

這個坑比較不直覺，但更致命。

想像有 100 個 client 在打同一個下游。下游掛掉，**這 100 個 client 在同一瞬間全部失敗**。

然後它們都套用指數退避，都等 1 秒。

```
t = 0.0s   100 個請求全部失敗
t = 1.0s   100 個請求同時重試 ← 全部撞在一起
t = 1.0s   下游剛要爬起來，又被 100 個請求打回去
t = 3.0s   100 個請求同時重試（等 2 秒）
t = 3.0s   又被打回去
...
```

**退避拉開了「你自己」兩次重試的間隔，卻讓「所有人」的重試同步化了。** 下游永遠在復原的那一刻被脈衝擊倒，震盪不會停。這叫 **thundering herd**（驚群效應）。

### 解法：加隨機（jitter）

不要都等剛好 1 秒，而是等「0.5 到 1 秒之間的隨機值」。

程式裡是這一行：

```go
return d/2 + rand.N(d/2)     // d = 1s 時，結果落在 [0.5s, 1s)
```

一半固定（`d/2`）、一半隨機（`rand.N(d/2)`），這種做法叫 **equal jitter**。

效果：

```
沒有 jitter：t = 1.0s 這一瞬間收到 100 個請求
有 jitter：  100 個請求隨機散布在 t = 0.5s ~ 1.0s 這 500ms 內
             → 平均每 5ms 才 1 個請求
```

**尖峰從「100 個同時」變成「一個一個慢慢來」。** 下游看到的是斜坡，不是脈衝，才有機會真的站起來。

## 三、但重試解不了第一節那場事故

> 對應流程圖：〈7. 三者的分工〉

回頭看。重試處理的是「等一下就會好」的故障。

第一節那場事故是 Redis **真的掛了**，不是抖一下。這時候重試不但沒用，還有害：

- 每次重試都要再付一次 3 秒的逾時
- 一個失敗請求變成 4 個失敗請求（原本 1 次 + 重試 3 次）
- 卡住的 goroutine 數量翻四倍

**重試會放大負載。** 在下游已經死掉的情況下，這是往火裡加油。

所以需要一個完全不同的機制：**知道什麼時候該放棄。**

## 四、熔斷器：學會放棄

> 對應流程圖：〈1. 熔斷器狀態機〉—— 三態轉換的完整圖

名字來自家裡的斷路器 —— 電流異常時直接斷開，保護的是**整棟房子的線路**，不是那個短路的電器。

熔斷器一樣：**它保護的不是 Redis，是你自己的延遲。**

### 基本想法

```
判定「這東西掛了」→ 之後的請求不要再打了，直接回錯誤
```

回到第一節的場景，加上熔斷器之後：

```
一開始的請求 → 各等 3 秒逾時 → 熔斷器判定 Redis 掛了
之後的請求   → 熔斷器直接擋下（0ms）→ 立刻去查 MySQL → 50ms 回應
```

**每個請求的延遲從 3050ms 回到 50ms。** 卡住的 goroutine 從 600 個回到接近 0。服務活著，只是沒有快取。

這叫**優雅降級（graceful degradation）** —— 功能打折，但不倒。

### 為什麼需要三個狀態

最直覺的設計是兩態：正常 / 熔斷。

問題是：**熔斷之後要怎麼知道對方好了？**

如果永遠不試，Redis 修好了你也不知道，會一直降級跑下去。
如果一直試，那就等於沒熔斷。

所以要第三態：

| 狀態 | 行為 | 目的 |
|---|---|---|
| **closed**（正常） | 全部放行 | 平常運作 |
| **open**（熔斷） | 全部擋掉 | 保護自己的延遲 |
| **half-open**（半開） | **只放一個**請求過去試探 | 用最小成本確認對方好了沒 |

half-open 是關鍵。它只犧牲一個請求去探路：

- 探測成功 → 回到 closed，恢復正常
- 探測失敗 → 回到 open，重新計時

**用一個請求的代價，換「不用一直瞎猜」。**

程式裡：`breakerCooldown = 10 * time.Second`，熔斷 10 秒後進入 half-open 放一個探測。
`probing` 這個布林值就是在確保「同時只有一個探測」，其他請求照擋。

## 五、怎麼判定「它掛了」

> 對應流程圖：〈3. record — 統計與熔斷判斷〉—— 分桶、樣本門檻、失敗率判斷的完整流程

上一節跳過了最重要的問題：**憑什麼說它掛了？**

### 直覺做法：連續失敗 N 次

```
失敗 失敗 失敗 失敗 失敗 → 熔斷
失敗 失敗 成功           → 計數歸零，重新數
```

只要一個整數就能實作，記憶體幾乎為零。低流量、故障型態單純（要嘛全好要嘛全掛）的情況下夠用。

### 但它有一個漏洞：混合流量

```
成功 成功 失敗 成功 失敗 成功 成功 失敗 成功 失敗 ...
```

失敗率 40%，明顯不健康。但**從來沒有連續 5 次失敗**，因為每次成功都把計數歸零 —— 熔斷器永遠不會開。

這種型態在真實系統很常見：

- Redis 有多條連線，其中幾條壞掉 → 打到壞連線的失敗，打到好連線的成功
- 叢集有一個節點異常 → 某些 key 失敗，其他正常
- 對方過載但沒死 → 一部分請求逾時，一部分擠進去了

**整體明顯有問題，但成功與失敗交錯出現。** 連續計數對這種情況完全失效。

### 改成：視窗內的失敗率

換個判斷方式：**過去 30 秒內，失敗比例超過一半就熔斷。**

這樣就跟「連續不連續」無關了，只看整體健康度。上面那個 40% 的例子會被抓到。

### 失敗率的陷阱：樣本數

但直接算比例有一個很容易踩到的坑：

```
視窗剛開始，第一個請求進來 → 失敗
失敗率 = 1/1 = 100% → 立刻熔斷
```

**一個偶然的抖動就把整個快取關掉 10 秒。** 比例在樣本少的時候完全沒有意義。

所以要一道門檻：

```go
if total < breakerMinRequests {
    return // 樣本不足，失敗率沒有意義
}
```

`breakerMinRequests = 20`。視窗內累積不到 20 筆，不做判斷。

**這是實務上最常被漏掉的一步。** 很多人寫熔斷器只算比例，然後在半夜低流量時段被一兩個逾時誤觸。

### 怎麼算視窗，又不把記憶體吃光

最直覺的做法是記下每一筆呼叫的時間戳，要算的時候把 30 秒內的挑出來。

問題是記憶體隨流量成長。1000 QPS × 30 秒 = 三萬筆時間戳，而且要不斷清理。

**解法：分桶。**

把 30 秒切成 6 個桶，每個桶涵蓋 5 秒。每個桶只存兩個數字：

```
桶 = { 總數, 失敗數 }
```

固定 6 個桶，**記憶體不隨流量成長**。一萬筆請求和一筆請求佔用一樣的空間。

### 桶怎麼知道自己過期了

用**絕對桶號**：

```go
idx  = now.UnixNano() / 5s   // 隨時間單調成長，永不重複
slot = idx % 6               // 環形緩衝的槽位，會循環使用
```

每個桶記下自己的 `idx`。存取時比對：

```go
slot := &b.buckets[idx%breakerBuckets]
if slot.idx != idx {
    *slot = bucket{idx: idx}   // 槽位裡是舊桶（繞了一圈），就地歸零重用
}
```

**好處：不需要背景 goroutine 定時清理。** 過期的判定發生在存取的那一刻 —— 你要用到這個槽位時，才檢查它裡面是不是舊資料。

加總視窗時也一樣，只挑桶號落在範圍內的：

```go
oldest := idx - breakerBuckets + 1
for _, bk := range b.buckets {
    if bk.idx >= oldest && bk.idx <= idx {
        total += bk.total
        failures += bk.failures
    }
}
```

沒有流量的那段時間，桶號會落在範圍外，自然被排除。

### 代價

視窗邊界是**階梯式**的，不是平滑滑動。最舊的桶會整桶掉出，而不是一筆一筆掉。

```
真正的滑動視窗：now - 30s 到 now
分桶的實際效果：涵蓋 25 ~ 30 秒之間，取決於當下在桶的哪個位置
```

誤差最多一個桶（5 秒）。要更精確就得回去記時間戳 —— 不值得。

## 六、走一遍程式碼

> 對應流程圖：`allow` 見〈1〉、`record` 見〈3〉、Hook 見〈2. 請求路徑〉

### `allow(now) bool` — 這次要不要放行

狀態先由 `currentState` 推導出來，再照狀態決定放不放行：

```go
func (b *breaker) currentState(now time.Time) state {
    switch {
    case b.openedAt.IsZero():
        return stateClosed
    case now.Sub(b.openedAt) < breakerCooldown:
        return stateOpen
    default:
        return stateHalfOpen
    }
}

func (b *breaker) allow(now time.Time) bool {
    switch b.currentState(now) {
    case stateClosed:
        return true
    case stateOpen:
        return false
    default: // half-open：只放行一個探測
        if b.probing {
            return false
        }
        b.probing = true
        return true
    }
}
```

### 為什麼狀態是推導的，不是存起來的

這是這份實作最容易被質疑的設計 —— 為什麼不乾脆存一個 `state` 欄位？

因為 **`open → half-open` 這個轉換沒有任何程式碼在執行**。它是時間走到了就發生的。

如果 `state` 是存起來的欄位，就沒有人會去把它從 `stateOpen` 改成 `stateHalfOpen`，除非你：

- 開一個背景 timer 去改 —— 多一個 goroutine 和它的生命週期問題
- 或在存取時才惰性計算 —— 那你還是需要 `openedAt`，於是同時有 `state` 和 `openedAt` **兩個真相來源**，每次改動都要記得同步，它們有機會不一致

所以真相來源只有 `openedAt` 和 `probing`，`state` 是它們的函數。enum 的價值在**命名**和**可斷言**，不在儲存。

### `record(now, failed)` — 記結果、推進狀態

分成三段。

**第一段：探測結果單獨處理**

```go
if b.probing {
    b.probing = false
    if failed {
        b.openedAt = now          // 回到 open，cooldown 重新計時
    } else {
        b.openedAt = time.Time{}  // 完全復原
        b.resetWindow()
    }
    return
}
```

探測**不進統計視窗**。它是單一樣本，本來就該一票決定去留 —— 丟進失敗率裡會被稀釋掉，探測失敗反而無法立即反應。

**第二段：記入當下的桶**

```go
bk := b.currentBucket(bucketIndex(now))
bk.total++
if failed { bk.failures++ }
```

**第三段：判斷要不要熔斷**

```go
if !b.openedAt.IsZero() { return }   // 已熔斷中，不重複判斷

total, failures := b.window(bucketIndex(now))
if total < breakerMinRequests { return }
if float64(failures)/float64(total) >= breakerFailureRate {
    b.openedAt = now
    b.resetWindow()
}
```

熔斷時要 `resetWindow()`。不清空的話，之後探測成功回到 closed，視窗裡還留著剛剛那批失敗 —— 一兩次新失敗就又把比例推過門檻，會在 open 和 closed 之間來回震盪。

### 怎麼接進去 — 這段是整個設計最漂亮的地方

熔斷器沒有寫進快取層，也沒有寫進 service 層。它是一個 **go-redis 的 Hook**：

```go
func (h breakerHook) ProcessHook(next rd.ProcessHook) rd.ProcessHook {
    return func(ctx context.Context, cmd rd.Cmder) error {
        if !h.b.allow(time.Now()) {
            cmd.SetErr(ErrBreakerOpen)
            return ErrBreakerOpen
        }
        err := next(ctx, cmd)
        h.b.record(time.Now(), isBreakerFailure(ctx, err))
        return err
    }
}
```

Hook 是 go-redis 官方提供的攔截點，**所有 Redis 指令都會經過這裡**。所以：

- 快取層的程式碼：一行都不用改
- Service 層的程式碼：一行都不用改
- 降級行為：**自動成立**

為什麼自動成立？因為 service 層本來就寫了「快取出錯就去查 DB」。而 `ErrBreakerOpen` 是一個錯誤，會沿著原本的錯誤路徑往上冒，觸發那條既有的降級邏輯。

熔斷器只是**製造了一個更快的失敗**，其餘照舊。

### `isBreakerFailure` — 不是每個錯誤都算失敗

```go
if err == nil || errors.Is(err, rd.Nil) { return false }
return ctx.Err() == nil
```

兩個例外要排除：

**1. `rd.Nil` 是快取未命中，不是故障。**
「這個 key 沒有資料」代表 Redis 活得很好、正常回答了你。把它算成失敗的話，快取命中率一低就會誤觸熔斷。

**2. 呼叫方自己取消，不是 Redis 的錯。**
使用者關掉瀏覽器、HTTP client 斷線，`ctx` 會被取消，Redis 呼叫也跟著失敗。但那是你這邊的事。如果算成 Redis 失敗，使用者一多、大家亂關頁面，熔斷器就被推開了 —— 而 Redis 明明好得很。

**這兩個判斷決定熔斷器準不準。** 少了它們，熔斷器會在不該熔斷的時候熔斷。

## 七、那些守衛在防什麼

> 對應流程圖：〈邊界守衛〉有七個守衛的一覽表，可當檢查清單

### 1. `breakerMinRequests` 樣本門檻

第五節講過：沒有它，視窗內第一個失敗就是 100% 失敗率，立刻熔斷。低流量時段最容易被一兩個逾時誤觸。

### 2. 熔斷與探測成功時 `resetWindow()`

不清空的話，恢復後舊失敗還留在視窗裡，一兩次新失敗就再次觸發，在 open / closed 之間來回震盪。

### 3. 過期桶就地歸零

```go
if slot.idx != idx {
    *slot = bucket{idx: idx}
}
```

環形緩衝繞一圈後會回到同一個槽位。不歸零就會把 30 秒前的統計累加到現在的視窗上。

### 4. 探測結果不進統計視窗

單一樣本被平均掉，探測失敗無法立即讓熔斷器重新關上。

### 5. 等待期間用 `select` 而不是 `time.Sleep`

```go
select {
case <-ctx.Done():                                     // 使用者取消了
    return cancelled
case <-time.After(backoffDelay(retryDelay, attempt)):  // 等到了，繼續重試
}
```

如果寫成 `time.Sleep(delay)`：使用者在等待期間取消請求，程式**還是會睡完整段時間**才發現。退避到後面可能是 8 秒、16 秒，那就是白佔 goroutine 16 秒。

### 6. `d <= 0` 抓位移溢位

```go
d := base << attempt
if d > maxBackoff || d <= 0 { d = maxBackoff }
```

`base << attempt` 是位元左移。`time.Duration` 底層是 int64，左移太多次會**溢位成負數**。

沒有 `d <= 0` 這個守衛，attempt 大到某個程度時 `d` 會變負數，`time.After(負數)` 會立刻觸發 —— **退避完全失效，變成瘋狂重試。** 而 `d > maxBackoff` 這個條件抓不到負數（負數比 maxBackoff 小）。

### 7. `maxRetry < 0` 修正為 0

迴圈是 `for attempt := 0; attempt <= maxRetry; attempt++`。`maxRetry` 是 -1 的話迴圈一次都不跑，`lastResponse` 保持 nil，跑到最後一行 `lastResponse.Message = ...` 就 **nil pointer dereference，直接 panic**。

## 八、為什麼熔斷器裝在 Redis 而不是 MySQL

> 對應流程圖：〈2. 請求路徑〉裡「降級查 DB」那條線就是這一節在講的替代路徑

因為**降級要有路可走**。

Redis 是快取，掛掉還能查 MySQL —— 慢一點但功能完整，所以「跳過 Redis」是有意義的。

MySQL 掛掉沒有替代路徑。裝熔斷器只是把「等 3 秒才失敗」變成「立刻失敗」，功能一樣是壞的。（快速失敗在某些設計裡仍有價值，但那是另一個目的，不是降級。）

**判斷準則：這個依賴掛掉時，有沒有第二條路？** 有 → 熔斷器 + 降級很有價值。沒有 → 先想清楚你要的到底是什麼。

## 九、還需要第三道：請求層逾時

> 對應流程圖：〈6. 請求層逾時〉

熔斷器只保護「你替它裝了熔斷器」的那個依賴。這個專案裝在 Redis 上 —— 那 MySQL 呢？第三方 API 呢？某個 handler 裡不小心寫出的慢查詢呢？

那些都沒有保護。而第一節那場事故的機制（請求卡住 → goroutine 堆積 → 服務死掉）**跟依賴是誰無關** —— 任何一個沒有上限的等待都會重演一次。

所以要一道與依賴無關的總上限：**這個請求最多跑 10 秒。**

### 做法：換掉 context，不是殺掉 handler

```go
ctx, cancel := context.WithTimeout(c.Request.Context(), d)
defer cancel()
c.Request = c.Request.WithContext(ctx)
c.Next()
```

Go 沒辦法從外面強制中斷一個 goroutine。能做的是**傳遞取消訊號**，靠下游自己去 respect 它。

GORM 和 go-redis 都吃 ctx —— deadline 到了，正在等的查詢會立刻回錯誤。而幾乎所有請求的時間都花在這些 I/O 上，所以這招覆蓋了實際會發生的問題。

### 代價

不吃 ctx 的東西切不斷。純 CPU 迴圈、`time.Sleep`、不接受 ctx 的第三方套件 —— 這些照樣跑完。

要硬上限，得把 handler 丟進 goroutine、緩衝整個回應、逾時就丟掉緩衝改寫 504。那會帶來雙寫競態與記憶體緩衝，而且被放生的 goroutine 還是在跑。**用這些複雜度換一個很少發生的情況，不值得。**

### 補 504 之前要先看有沒有寫過

```go
if errors.Is(ctx.Err(), context.DeadlineExceeded) && !c.Writer.Written() {
    c.AbortWithStatusJSON(http.StatusGatewayTimeout, ...)
}
```

`c.Writer.Written()` 這個判斷不能省。handler 已經回了 200 和一份 JSON，你再寫 504 —— 狀態碼早就送出去了，Gin 只會印 `superfluous WriteHeader` 警告，客戶端拿到的還是 200。硬改沒有意義，只會蓋掉真實的狀態。

### 哪些路徑要豁免

| 路徑 | 理由 |
|---|---|
| `/stream/` | SSE 與 chunked 本來就要長時間開著，套逾時等於功能壞掉 |
| `/socket.io/` | WebSocket 同上 |
| `/tasks/` | 重試鏈總長由請求參數決定（`maxRetry` × backoff），可能合法超過 10 秒；且任務層自己已有 `context.WithTimeout` |

**長連線與逾時天生衝突。** 任何全域逾時都要留豁免清單，否則第一個被打斷的就是你的 SSE。

## 十、目前的限制

> 對應流程圖：〈已知限制〉

**視窗邊界是階梯式的。** 分桶的代價，誤差最多 5 秒。第五節結尾講過。

**`breakerMinRequests = 20` 需要流量才有判斷力。** 20 筆 / 30 秒約等於 0.67 QPS。低於這個流量的環境，熔斷器實質上永遠不會作用 —— 因為樣本永遠不足。這是這個門檻的必然代價：它一邊防誤觸，一邊也讓低流量下失去保護。

如果部署環境流量很低，這個常數要往下調。**它是這份實作最主要的校準旋鈕。**

## 十一、一頁總結

> 對應流程圖：〈7. 三者的分工〉

| | Retry + backoff + jitter | Circuit Breaker | 請求層 Timeout |
|---|---|---|---|
| 處理什麼 | 等一下就會好的故障 | 已知的依賴掛了 | 沒有熔斷器保護的任何慢 |
| 時間尺度 | 秒 | 分鐘 | 秒 |
| 策略 | 撐過去 | 放棄，走替代路徑 | 給整個請求一個上限 |
| 判斷依據 | 呼叫失敗了 | 視窗內失敗率 + 最小樣本數 | 時間到了 |
| 保護對象 | 下游（不補刀）+ 自己（拿到結果） | 自己的延遲與資源 | 自己的 goroutine 與連線 |
| 沒有它會怎樣 | 重試放大負載，把下游打得更慘 | 每個請求都付滿逾時，被依賴拖死 | 任何漏網的慢都能把服務堆死 |

**Retry 與熔斷器必須成對**：重試負責「小病自己撐過去」，熔斷器負責「大病別硬撐」。

**請求層逾時是最後一道網**：熔斷器只保護有裝的依賴，逾時保護所有沒被涵蓋的慢。
